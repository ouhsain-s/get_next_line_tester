# get_next_line_tester — Comprehensive Usage Guide

This document explains how to install, build, run and debug the `get_next_line_tester` suite. It assumes you drop the `get_next_line_tester` folder inside the root of a project that provides the `get_next_line` sources and headers (mandatory and/or bonus). The guide covers mandatory tests, bonus tests, multi-file (multi-FD) tests, Valgrind use, common troubleshooting and practical examples.

---

# 1. Overview

`get_next_line_tester` is a portable testing helper folder that you can copy into any C project that implements `get_next_line`. Place the `get_next_line_tester` directory inside the project root. The tester will compile against sources found in the parent directory (project root). It supports:

* Mandatory `get_next_line` tests (builds and runs `tst_mandatory`).
* Bonus `get_next_line_bonus` tests (builds and runs `tst_bonus`), if bonus sources exist.
* Multi-FD tests for reading from multiple files at once (`tst_bonus_with_yourfiles`).
* Valgrind targets for memory checking.
* Simple autogenerated test files (small, big, empty, no-newline) created at runtime by testers and cleaned up automatically.

---

# 2. Expected project layout

Put `get_next_line_tester` inside your project root. Example layout:

```
project/
├─ get_next_line.c
├─ get_next_line_utils.c
├─ get_next_line.h
├─ get_next_line_bonus.c        # optional
├─ get_next_line_utils_bonus.c  # optional
├─ get_next_line_bonus.h        # optional
└─ get_next_line_tester/
   ├─ Makefile
   ├─ tst_mandatory.c
   ├─ tst_bonus.c
   └─ tst_bonus_with_yourfiles.c
```

**Important:** The tester looks for the `get_next_line` sources in the parent directory using `../get_next_line*.c` and `../get_next_line*.h`. Do not move the tester outside the project root unless you change the paths.

---

# 3. Prerequisites

* A Unix-like environment (Linux, macOS). On macOS, use `brew install valgrind` if you need Valgrind (Valgrind for macOS may be limited).
* A C compiler (e.g. `cc`/`gcc`/`clang`).
* `make` (GNU make recommended).
* `valgrind` for memory checks (optional but recommended).

---

# 4. Quick start — build everything

Open a terminal in the `get_next_line_tester` directory and run:

```bash
cd get_next_line_tester
make
```

* `make` builds `tst_mandatory` always. It will also build `tst_bonus` and `tst_bonus_with_yourfiles` if the bonus sources exist in the project root.
* The build macro `BUFFER_SIZE` defaults to `21` but you can override it when running `make`:

```bash
make BUFFER=100
```

---

# 5. Running tests (no Valgrind)

* Run the mandatory tester:

```bash
make run-mandatory
```

* Run the bonus tester (only if bonus sources exist):

```bash
make run-bonus
```

* Run the multi-FD tester (pass `ARGS` listing files to read). Files should typically be referenced from the project root; the tester accepts relative paths. Example:

```bash
make run-bonus-yourfiles ARGS="../file1.txt ../file2.txt ../file3.txt"
```

Note: `ARGS` is used because calling `make` with extra positional arguments treats them as targets. Use the `ARGS` variable to supply runtime file arguments.

---

# 6. Running tests with Valgrind

Valgrind targets guarantee the tester binary is built first and then run under Valgrind.

* Valgrind on mandatory tester:

```bash
make valgrind-mandatory
```

* Valgrind on bonus tester (if present):

```bash
make valgrind-bonus
```

* Valgrind on multi-FD tester (supply `ARGS`):

```bash
make valgrind-bonus-yourfiles ARGS="../file1.txt ../file2.txt"
```

Valgrind output will print memory leaks, invalid reads/writes and general memory usage. Look for "All heap blocks were freed" or any reported errors. Use `--track-origins=yes` (already enabled in the Makefile) to track where uninitialized values come from.

---

# 7. Testers behavior & generated files

Each tester creates small helper files in the current directory while running, then removes them when finished:

* `tst_mandatory` creates: `test_small.txt`, `test_big.txt`, `test_empty.txt`, `test_nonewline.txt`.
* `tst_bonus` creates: `bonus_test_small.txt`, `bonus_test_big.txt`, `bonus_test_empty.txt`, `bonus_test_nonewline.txt`.

These files are removed by the testers at the end. If a tester crashes, you may find leftover files; remove them manually.

---

# 8. Changing BUFFER_SIZE

`BUFFER_SIZE` controls how many bytes are read at once by `read()` inside `get_next_line`. The Makefile defines `BUFFER` variable that becomes the macro `BUFFER_SIZE` passed to the compiler. Examples:

```bash
make BUFFER=1        # very small buffer
make BUFFER=42       # custom buffer
make valgrind-bonus BUFFER=100
```

Set `BUFFER` to different values to exercise edge cases in your implementation.

# 9. Common problems & troubleshooting

**1) "Mandatory GNL sources not found" error at `make`**

```
$(error Mandatory GNL sources not found in parent dir ...)
```

Cause: the tester expects `../get_next_line.c` and `../get_next_line_utils.c` to exist. Fix: copy your `get_next_line` sources into the project root (parent of `get_next_line_tester`) or adjust the Makefile paths.

**2) `tst_bonus` binary missing / "No such file or directory" when running valgrind**

Run `make` (or `make valgrind-bonus`) to build the binary first. The updated Makefile already makes sure the binary is built before running Valgrind.

**3) Passing files to `run-bonus-yourfiles` or `valgrind-bonus-yourfiles`**

Do not pass files directly after `make` like `make valgrind-bonus-yourfiles ../f1 ../f2`. Instead use `ARGS`:

```bash
make run-bonus-yourfiles ARGS="../f1 ../f2"
```

**4) `BUFFER` vs `BUFFER_SIZE` compile error**

If you get `use of undeclared identifier 'BUFFER'`, ensure the test source uses `BUFFER_SIZE` (that's the macro the Makefile defines). The provided sources use `BUFFER_SIZE`.

**5) Valgrind on macOS**

Valgrind support on macOS is limited. If Valgrind is missing, install it using Homebrew if a compatible release exists, or run tests on Linux for full Valgrind support.

**6) Leftover test files after crash**

Remove them manually: `rm get_next_line_tester/test_*.txt bonus_test_*.txt` or run `make clean` in the tester folder.

# 10. Examples (real commands)

Build all available testers with default BUFFER:

```bash
cd get_next_line_tester
make
```

Run mandatory tests:

```bash
make run-mandatory
```

Run bonus tests under Valgrind (if present):

```bash
make valgrind-bonus BUFFER=10
```

Run multi-FD tester on three files from project root under Valgrind:

```bash

```

# 11. Tips for efficient debugging

* Run `make valgrind-*` with small `BUFFER` values (e.g. `BUFFER=1`) to exercise tricky buffer edge cases.
* If you see uninitialized value warnings from Valgrind, re-run with `--track-origins=yes` (already enabled) to find the source.
* Use `printf` debugging in small isolated test files to reproduce the failing sequence slowly.
* Add `-g` to `CFLAGS` in the Makefile if you want better debug symbols (e.g. `CFLAGS := -Wall -Wextra -Werror -g`).

---

# 12. Extending or customizing the tester

* To change the test files' content, edit the `make_test_files()` functions inside `tst_mandatory.c` and `tst_bonus.c`.
* To change where test binaries are placed, alter the `-o` flags in the Makefile targets.
* To make the tester look in a different directory for the GNL sources, change the `../` prefixes in the Makefile to the correct relative path.

---

# 13. FAQ

**Q: Can I test only one specific test (e.g., big file performance)?**
A: Yes — edit the tester source or compile it manually and run it directly, or temporarily comment other test calls in the `main()`.

**Q: Can I pass files without `../`?**
A: Yes — pass paths relative to the tester binary. For convenience, you can use `ARGS="file1 file2"` if the files are in the tester directory, or `ARGS="../file1"` if they are in project root.

**Q: Will this modify my project sources?**
A: No — the testers create temporary text files and binaries inside the tester folder. They compile project sources by referencing them in the parent directory but do not change them.
